# 03 企业内部知识问答（RAG + SFT）

企业知识问答先解决三个问题：证据从哪里来、没有答案时怎么办、用户能看到哪些内容。文档经过解析、分块和索引后，问题同时走 BM25 与向量检索，再融合、重排，把最相关的证据交给模型。SFT 训练证据使用、引用和拒答，不用来把企业知识“背进参数”。

仓库保留算法链路里真正需要讲清楚的步骤，不包含前后端。示例文档和问答均为合成数据，不能替代真实公司的权限、审计和数据治理系统。

## 1. 做完后要留下什么

做完后应保留：

- 带 `doc_id`、标题、页码、版本、部门和访问范围的文档块；
- BM25、Dense、Hybrid、Hybrid + Reranker 四组检索对照；
- 能按证据回答、标注来源并处理无答案问题的 LoRA SFT 模型；
- 固定测试集上的 Recall@5、MRR@10、nDCG@10、答案正确率、引用正确率和拒答召回率；
- 按问题类型、文档版本和权限范围整理的失败样例；
- 一条能追溯到用户、索引版本、文档和 chunk 的查询日志。

## 2. 项目主线

```text
PDF / Word / Markdown
  -> 解析正文和标题层级
  -> 按标题分块，写入版本与 ACL 元数据
  -> BM25 + BGE-M3 Dense Retrieval
  -> RRF 融合候选
  -> bge-reranker-v2-m3 重排
  -> 取 Top-5 证据
  -> Qwen3 按证据回答、引用或拒答
  -> 构造带上下文的 SFT 数据
  -> Base-RAG / SFT-RAG 对照评估
```

这里把边界分得很清楚：频繁变化的制度、产品说明和流程放在知识库里更新，SFT 只训练模型怎样筛选证据、引用证据和处理无答案问题。训练样本同时放入相关块与干扰块，否则模型在离线数据里只会读“完美上下文”，遇到真实检索噪声很容易失效。

## 3. 目录里有什么

- [`prepare_documents.py`](./scripts/prepare_documents.py)：清洗文档并生成带元数据的 chunk。
- [`build_sft_data.py`](./scripts/build_sft_data.py)：把问答、正例证据和干扰证据组装成 SFT `messages`。
- [`chunking.py`](./src/enterprise_rag/chunking.py)：按标题和段落切块，保留可追溯元数据。
- [`retrieval.py`](./src/enterprise_rag/retrieval.py)：ACL 前置过滤、RRF 融合和重排接口。
- [`prompting.py`](./src/enterprise_rag/prompting.py)：证据边界、引用格式和拒答约束。
- [`evaluation.py`](./src/enterprise_rag/evaluation.py)：检索、引用和拒答指标。
- [`rag_qwen3_lora_sft.yaml`](./configs/rag_qwen3_lora_sft.yaml)：LLaMA-Factory 的 LoRA SFT 配置起点。
- [`evaluation.md`](./docs/evaluation.md)：固定评测表和消融实验记录。

## 4. 先把知识库边界写清楚

第一版可以只选员工制度、报销流程、IT 操作手册和产品 FAQ 四类文档。每份文档至少保留这些字段：

| 字段 | 用途 |
| --- | --- |
| `doc_id` / `chunk_id` | 回溯原文并生成引用 |
| `title` / `section` / `page` | 给回答提供可读来源 |
| `version` / `effective_at` | 避免新旧制度混用 |
| `department` / `acl_groups` | 在检索前限制候选范围 |
| `content_hash` | 判断文档是否变化，支持增量重建索引 |

不要先把所有文档召回，再在生成结束后删除越权内容。没有访问权限的 chunk 不应进入候选集，更不应进入模型上下文。生产系统还要把用户身份、权限快照、索引版本和最终引用写入审计日志。

## 5. 文档分块不是固定公式

示例代码先按标题层级和段落切分，再把过长段落滑窗拆开。`max_chars=600`、`overlap_chars=80` 只是中文文档的实验起点，不是行业标准。选择时要同时看：

- 一个 chunk 能否独立回答问题；
- 标题、表格说明和限定条件是否被拆散；
- 召回率是否提升，送进重排和生成的 Token 是否可控；
- 同一答案需要跨多个 chunk 时，是否要保留父标题或相邻块。

切分策略要进入消融实验。只报告“使用了 500 字分块”，却没有说明为什么，面试时很容易被追问。

## 6. 混合检索与重排

BGE-M3 同时支持 dense、sparse 和 multi-vector 检索，也覆盖多语言。这个示例只使用它的 dense embedding；关键词侧单独用 BM25，便于把两路召回独立评估。

两路候选用 Reciprocal Rank Fusion 合并：

```text
RRF(d) = sum(1 / (k + rank_i(d)))
```

RRF 只依赖名次，不要求 BM25 分数和向量相似度处在同一量纲。`k=60` 是原论文使用并讨论过的设置，可以作为起点，但仍应在验证集上比较。融合后取较大的候选池，再交给 `bge-reranker-v2-m3`。它直接接收 query-passage 对并输出相关性分数，和先独立编码文本的 embedding 模型角色不同。

FAISS 用来存储和搜索 dense vector。它支持 L2 和点积等相似度搜索；在这个教学规模中可从精确的 `IndexFlatIP` 开始，语料变大后再比较近似索引，不能在没测召回损失前只追求速度。

## 7. RAG 提示与 SFT 数据

生成提示要把检索内容标成“不可信数据”，并要求模型只根据证据作答：

```text
证据足够：给出结论，并在句末引用 [doc_id#chunk_id]
证据不足：回答“当前知识库没有足够依据”，说明需要补充什么
证据冲突：指出版本或口径冲突，不擅自选一个答案
```

SFT 样本包含 question、正例 chunk、干扰 chunk 和标准回答。训练目标有三类：

1. 从多个 chunk 中找到真正支持答案的内容；
2. 让答案中的事实与引用对齐；
3. 在无答案、旧版本冲突或权限不足时拒答或升级处理。

这和把企业文档直接做成“背诵式问答”不同。文档更新时先更新索引；只有回答行为、引用格式或拒答边界发生系统性问题时，才考虑重新做 SFT。

## 8. LoRA SFT

示例基座是 `Qwen/Qwen3-4B-Instruct-2507`，配置从 LoRA 开始：

```powershell
llamafactory-cli train configs/rag_qwen3_lora_sft.yaml
```

训练集与测试集必须按文档或文档族分组切分，不能让同一制度的不同改写同时出现在两边。SFT 输入中要混入检索产生的真实干扰块；只用一个完美正例训练，会让离线训练分数很好看，但模型在真实检索噪声下不会筛证据。

## 9. 评估与消融

检索和生成要分开测。检索失败时，模型不可能凭空给出有依据的答案；检索正确但回答错误，才是生成侧问题。

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Recall@5 | 前 5 个结果覆盖了多少标注相关 chunk |
| 检索 | MRR@10 | 第一个相关 chunk 排得是否靠前 |
| 检索 | nDCG@10 | 多个不同相关度结果的排序质量 |
| 生成 | 答案正确率 | 结论与人工金标是否一致 |
| 生成 | 引用正确率 | 引用 chunk 是否真的支持对应结论 |
| 生成 | Faithfulness | 回答中的事实是否能被检索上下文支持 |
| 边界 | 拒答召回率 | 无答案问题中有多少被正确拒答 |

至少保留四个检索版本：BM25、Dense、Hybrid、Hybrid + Reranker；再固定最好的一版检索，对比 Base-RAG 与 SFT-RAG。这样才能判断提升来自检索还是 SFT。

## 10. 安全与审计

企业 RAG 不能只讨论准确率。检索文档可能包含“忽略此前要求”一类间接提示注入。工程上要把检索内容标成不可信数据并用分隔符隔开，限制进入上下文的 chunk 数量与总长度，检测可疑指令，并在检索阶段执行最小权限过滤。

本项目至少记录：`user_id`、`acl_snapshot`、`query_id`、`index_version`、候选 `chunk_id`、最终引用、模型版本和拒答原因。日志中不要写入不必要的完整敏感正文。

## 11. 简历上怎么写

下面按 4B 模型、1.8 万级 chunk 和单机 LoRA 的项目量级给出一组完整写法。**这些数字不是当前仓库的实测成绩**；要先在自己的固定测试集上完成实验，再替换成实测结果。

**项目名称：企业内部知识问答系统**

**技术栈：Qwen3、LLaMA-Factory、LoRA、BGE-M3、BM25、RRF、BGE Reranker、FAISS、RAG**

- 面向员工制度、报销流程、IT 手册和产品 FAQ，整理 1200 份合成企业文档并生成 1.84 万个带标题、版本、页码和 ACL 标签的 chunk，构建 2400 条问答数据，按文档族切分为 1800/300/300，避免同源内容泄漏；
- 搭建 BM25 + BGE-M3 双路召回、RRF 融合与 `bge-reranker-v2-m3` 重排链路，在测试集 220 条可回答问题上，Recall@5 由 Dense 基线的 71.8%（158/220）提升到 84.1%（185/220），nDCG@10 由 0.61 提升到 0.72；
- 基于 Qwen3-4B 完成带正例证据、干扰证据、引用和拒答样本的 LoRA SFT；固定同一检索结果后，答案正确率由 70.0%（154/220）提升到 81.8%（180/220），引用正确率由 78.2%（172/220）提升到 89.1%（196/220）；
- 为 80 条知识库无答案问题设计拒答评测，拒答召回率由 62.5%（50/80）提升到 82.5%（66/80）；在召回前执行 ACL 过滤，并记录索引版本、候选 chunk 与最终引用，支持权限与答案溯源。

## 12. 面试官可能怎么问

### 12.1 企业知识为什么不能只靠 SFT 记住？

回答要点：企业制度和产品信息会更新，SFT 参数不能提供可靠的版本溯源，也不适合每次文档变化都重训。RAG 负责读取可更新、可引用、可做权限控制的外部知识；SFT 负责让模型更稳定地筛选证据、按证据回答和在证据不足时拒答。

### 12.2 chunk 大小和 overlap 怎么选？

回答要点：没有通用最优值。先看文档结构和答案跨度，设几个候选方案，在同一问题集上比较 Recall@k、nDCG、进入上下文的 Token 数和跨块失败样例。标题、限定条件、表格说明等语义单元优先保持完整。

### 12.3 为什么同时用 BM25 和 Dense Retrieval？

回答要点：BM25 对产品名、制度编号和错误码等精确词项很敏感；Dense Retrieval 更擅长语义改写。两路各有盲区，先独立评估，再用 RRF 等方法融合排名，不能假设混合后一定提升。

### 12.4 为什么召回后还要 Reranker？

回答要点：第一阶段需要在大量 chunk 中高召回，通常使用可预计算文档向量的双编码器；Reranker 联合读取 query 和 passage，相关性判断更细，但计算更贵，所以只处理前几十个候选。

### 12.5 SFT 在 RAG 里到底学什么？

回答要点：学习识别支持答案的证据、忽略干扰块、按固定格式引用、处理冲突版本和无答案问题。它不负责替代索引，也不能保证模型永久记住最新企业知识。

### 12.6 怎样构造无答案样本？

回答要点：从知识库覆盖范围外的问题、删除关键证据后的问题、只有旧版本或互相冲突证据的问题中构造，并由人工确认当前索引确实没有充分依据。只改几个关键词造“伪无答案”容易产生捷径。

### 12.7 怎样证明提升来自 SFT，而不是检索变好了？

回答要点：固定检索器、索引版本、Top-k 证据和解码配置，只替换 Base 与 SFT checkpoint；同时单独报告检索指标。若两次实验输入证据不同，就不能把端到端提升归因给 SFT。

### 12.8 如何评估引用是否正确？

回答要点：先解析回答中的 `doc_id#chunk_id`，再判断引用是否存在、是否有权限、是否包含支持该结论的证据。引用格式正确不等于引用内容正确，最好把关键 claim 与证据逐项对齐抽查。

### 12.9 权限过滤应该放在哪一步？

回答要点：应在召回前或召回查询内部完成，让无权限 chunk 不进入候选集。只在生成后遮盖文本，仍可能让模型看到、利用或泄露越权信息。还要固定权限快照并记录到查询日志。

### 12.10 如何防止检索文档里的 Prompt Injection？

回答要点：把检索文本明确标成不可信数据，用分隔符隔离；限制 chunk 数与总长度；检测可疑指令；不给问答模型不必要的工具和数据权限；用攻击样本持续评估。仅靠一句 system prompt 不能保证安全。
