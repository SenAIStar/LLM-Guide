# 怎么评估这个项目

先保存同一批测试样本在基础模型上的输出，再用完全相同的 Prompt、chat template 和解码参数测试 SFT 模型。否则结果变好以后，很难判断是微调带来的，还是测试配置变了。

## 自动指标

自动指标要跟任务类型对应。

| 任务 | 可以报告的指标 | 说明 |
| --- | --- | --- |
| 罪名、案由、争议类型等分类 | Accuracy、Macro-F1 | Macro-F1 能看到小类别是否被忽略 |
| 固定答案的法律知识题 | Exact Match 或任务官方指标 | 先统一答案格式，再计算 |
| 开放式法律问答 | 输出覆盖率只做健康检查 | 不能把“生成了文字”当成回答正确 |

[`evaluation.py`](../src/legal_qa/evaluation.py) 只实现分类指标和空输出检查。LawBench 自带不同任务的评价方式，跑外部评测时按它的任务定义出分，不自己发明一个总分。

## 人工评估

开放式回答建议抽样做盲评，至少检查：

1. 是否理解了问题和关键事实；
2. 是否出现虚构的法条、案例或事实；
3. 分析过程是否前后矛盾；
4. 结论是否保留了必要条件和边界；
5. 信息不足时是否明确说明缺口。

把基础模型和 SFT 模型的答案打乱顺序后交给评审，保留每条样本的分数和错误标签。最后除了平均分，还要列出典型失败样例，因为这部分最能说明下一轮数据该怎么补。

## 最小实验表

| 实验 | 训练数据 | 目的 |
| --- | --- | --- |
| Base | 不微调 | 得到基础模型基线 |
| SFT-Pair | Pair 数据 | 看法律任务表达和标签任务是否改善 |
| SFT-Mix | Pair + Triplet | 看混合数据是否带来增益或领域偏移 |

每组实验固定测试集和推理参数，并记录模型 revision、数据 hash、随机种子、LoRA 参数和 checkpoint。
