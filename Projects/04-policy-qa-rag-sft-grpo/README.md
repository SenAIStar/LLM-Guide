# 04 政策智能问答系统（RAG + SFT + GRPO）

政策问答的难点不只是“能不能搜到”，还要判断地区、时间、适用对象和文件版本。这个项目把这些条件放在检索前处理，再用 SFT 训练证据使用与拒答行为，最后用 GRPO 优化引用、边界和合规性。

仓库保留数据结构、过滤、检索融合、奖励和评估的核心代码。示例政策全部是合成数据，只用于说明字段和流程。

## 1. 做完后要留下什么

- 一套带来源、地区、适用对象、生效区间和版本状态的政策 chunk；
- BM25、Dense、Hybrid、Hybrid + Reranker 四组检索结果；
- Base-RAG、SFT-RAG、SFT + GRPO 三组同口径生成结果；
- 可回答、无答案、版本冲突和权限不足四类测试集；
- 逐题证据、引用判断、奖励分解和失败样例。

模型能答对几道题只是最终结果。面试时更重要的是讲清楚：适用性过滤放在哪里，SFT 学了什么，GRPO 奖励能否被规则验证，以及提升到底来自检索还是后训练。

## 2. 整体链路

```text
政策文件
  -> 解析条款、地区、主体、生效区间和版本
  -> 按政策族切分 train/dev/test
  -> 解析查询中的地区、日期和主体
  -> 有效版本与 ACL 前置过滤
  -> BM25 + Dense -> RRF -> Reranker
  -> Qwen3 按证据回答、引用、澄清或拒答
  -> LoRA SFT
  -> GRPO：正确性 + 引用 + 边界 + 安全
  -> 检索、生成、边界三层评估
```

## 3. 政策数据怎么整理

每个 chunk 至少保留：

| 字段 | 用途 |
| --- | --- |
| `document_id` / `chunk_id` | 追溯原文和生成引用 |
| `issuer` / `region` / `audience` | 判断政策适用范围 |
| `effective_from` / `effective_to` | 过滤未生效和已失效版本 |
| `status` / `version` | 处理新旧文件与废止关系 |
| `section_path` / `text` | 保留条款结构和正文 |
| `source_url` / `content_hash` | 回查来源、发现内容变更 |
| `acl_groups` | 限制可见范围 |

同一政策的正文、解读、附件和旧版本要用 `policy_family_id` 关联。训练集与测试集按政策族切分，不能把相邻条款随机拆开，否则测试结果会被同源文本抬高。

## 4. 先过滤，再检索

查询先解析 `as_of`、地区、主体类型和用户权限，再筛出可用 chunk。向量相似度只能表示文本接近，不能判断政策是否仍然有效，也不能判断当前用户是否适用。

[`pipeline.py`](./src/policy_qa/pipeline.py) 中的 `filter_before_retrieval` 展示了日期、地区和 ACL 的前置过滤。真实项目还要处理全国政策与地方政策的继承关系、政策状态变更、权限快照和过滤失败时的 fail-closed 行为。

## 5. 混合检索与重排

BM25 负责政策编号、条款名和精确术语，Dense Retrieval 负责口语化改写。两路各取 Top-50，用 RRF 按排名融合，再让 Cross-Encoder 重排并取 Top-5。

RRF 不直接相加 BM25 分数和向量相似度，避免两种分数尺度不一致。`k=60`、候选数 50 和最终 Top-5 都是实验起点，要在验证集上比较召回、排序质量、Token 开销和延迟。

## 6. SFT 训练什么

SFT 不负责记住全部政策。它训练四类行为：

1. 从相关块与干扰块中找到真正支持结论的证据；
2. 按 `[chunk_id]` 对齐引用，不伪造来源；
3. 发现旧版本、跨地区或主体冲突时说明冲突；
4. 证据不足、无权限或过滤失败时拒答或要求补充条件。

训练样本要混入旧版本 hard negative、相似地区政策和缺少关键条款的上下文。只给完美正例，模型学不到真实检索噪声下的判断。

## 7. GRPO 怎么做

对同一问题采样一组回答，先得到确定性检查和人工/模型评审信号，再计算组内相对优势。奖励可以拆成：

- 答案是否与金标结论一致；
- 引用 ID 是否存在、有效且当前用户可见；
- 证据是否支持对应 claim；
- 无答案、冲突和权限不足时是否正确处理；
- 越权证据、无效引用和无支持结论的惩罚。

[`rewards.py`](./src/policy_qa/rewards.py) 给出了奖励组合和组内标准化。格式、引用存在性、版本有效性和 ACL 应优先用程序检查。学习型评审只能补充语义判断，不能单独决定全部奖励。

`configs/grpo.yaml` 是奖励与训练预算的设计稿，不是与任意 VeRL 版本都兼容的启动配置。真正训练时要固定 VeRL commit，再按该版本的配置树接入奖励函数。

## 8. 评估与消融

检索侧报告 Recall@5、MRR@10、nDCG@10、有效版本命中率和越权候选率；生成侧报告答案正确率、claim 级引用正确率和引用覆盖率；边界侧报告拒答/澄清正确率、越权泄露率和无效引用率。

实验按两步做：

1. 固定生成模型，比较 BM25、Dense、Hybrid、Hybrid + Reranker；
2. 固定索引和 Top-5 证据，比较 Base、SFT、SFT + GRPO。

至少移除一次版本过滤、旧版本 hard negative、引用奖励和拒答奖励。每组都保存逐题结果，重点看“召回错”“版本选错”“有证据但答错”“引用不支持结论”和“本应回答却拒答”五类失败。

## 9. 代码从哪里看

- [`pipeline.py`](./src/policy_qa/pipeline.py)：政策对象、适用性过滤、RRF、证据提示和检索接口；
- [`sft.py`](./src/policy_qa/sft.py)：把固定检索结果组装成可追踪的 SFT `messages`；
- [`rewards.py`](./src/policy_qa/rewards.py)：可分解奖励和 GRPO 组内优势；
- [`evaluation.py`](./src/policy_qa/evaluation.py)：检索与边界指标汇总；
- [`grpo.yaml`](./configs/grpo.yaml)：group size、长度预算和奖励权重起点；
- [`data/sample`](./data/sample/)：字段完整的合成政策与问答样例。

## 10. 简历怎么写

下面的数字只演示简历结果如何对齐，**不是仓库实测**。完成自己的实验后，替换数据量、分母、原始计数和指标。

**政策智能问答系统｜Qwen3、LoRA、BGE-M3、BM25、RRF、BGE Reranker、FAISS、GRPO、VeRL**

- 整理 2000 份政策文件并解析为 27600 个带地区、发文机关、生效时间和版本状态的 chunk，构建 3600 条问答，按政策族切分为 2800/400/400；
- 搭建元数据过滤、BM25 + BGE-M3 双路召回、RRF 融合与 reranker 重排，在 300 条可回答测试问题上将 Recall@5 由 72.0%（216/300）提升到 83.7%（251/300）；
- 基于 Qwen3-4B 完成证据使用、版本冲突、引用和拒答 LoRA SFT，固定检索结果后将答案正确率由 72.7%（218/300）提升到 82.0%（246/300）；
- 设计可验证的 GRPO 奖励，在 400 条测试集上将政策合规正确率由 80.8%（323/400）提升到 87.3%（349/400），无效引用率由 6.0%（24/400）降至 2.5%（10/400）。

## 11. 面试官可能会问

**为什么政策问答不能只做向量检索？**

回答要点：政策编号和精确术语常由 BM25 召回，口语改写更适合 Dense；地区、时间、主体和权限则属于适用性条件，必须在相关性检索前处理。

**SFT 和 RAG 分别解决什么？**

回答要点：RAG 管理可更新、可引用的外部政策；SFT 训练模型筛选证据、处理冲突、引用和拒答。政策变化通常更新文档与索引，不靠重新微调记住新内容。

**为什么还要做 GRPO？**

回答要点：SFT 模仿示范答案，GRPO 直接优化一组候选中的相对质量。这个项目的引用合法性、版本有效性和拒答边界有较多可验证信号，适合组合奖励；是否有收益仍由 SFT/GRPO 对照实验判断。

**怎样检查引用正确？**

回答要点：先检查引用 ID 是否存在、版本是否有效、用户是否有权限，再把答案拆成 claim，逐项判断证据是否支持。格式正确不代表内容正确。

**如何发现 reward hacking？**

回答要点：监控各奖励项、答案长度、重复引用和拒答比例，抽查高奖励低质量样本，并在未参与奖励设计的盲测集上做最终判断。

**怎样证明提升来自 GRPO？**

回答要点：固定 SFT checkpoint、索引、Top-k、prompt 和解码配置，只改变后训练阶段；同时报告奖励曲线、盲评、边界指标和退化项。
