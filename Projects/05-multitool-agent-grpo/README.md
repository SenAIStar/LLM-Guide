# 05 多功能任务智能体（Agent + GRPO）

先把任务范围收紧：Agent 只需要选择工具、填写参数、读取 observation，并在有限步数内完成目标。第一版包含计算器、文件只读、日历查询、邮件草稿、待办事项和 Web 搜索六类 mock 工具。所有动作都在内存状态或固定快照中执行，不发送邮件、不修改真实日历，也不访问本机文件。

项目最后看环境终态，不采信模型自己说“已经完成”。这也是工具 Agent 和普通对话项目最关键的区别。

## 1. 做完后要留下什么

- 一套明确的工具 schema、权限表和统一错误码；
- 单工具、多工具、缺参追问、失败恢复和拒绝执行任务；
- 可回放的 action/observation 轨迹与环境终态；
- Base/SFT 或 Prompt baseline 与 GRPO 的同口径结果；
- 非法调用、循环、越权、提示注入和终态不一致的失败样例。

## 2. Agent 循环

```text
用户任务 + 初始状态 + 可用工具
  -> policy 输出 JSON action
  -> action 类型、参数和权限校验
  -> mock 工具执行
  -> observation 写回轨迹
  -> 继续调用或输出 final
  -> 比较最终状态与 goal state
  -> 计算轨迹奖励
```

[`agent.py`](./src/multitool_agent/agent.py) 负责最大步数、JSON 校验、重复 action 检测和终态记录。执行器遇到未知 action、非法参数或未授权工具时返回结构化错误，不让异常直接打断整批 rollout。

## 3. 工具协议与权限

模型的工具动作保持简单：

```json
{
  "type": "tool",
  "tool_name": "calendar.query",
  "arguments": {"start": "2026-07-30T14:00:00+08:00"}
}
```

执行器负责四件事：工具是否在 allowlist、参数能否通过 schema、动作是否允许产生副作用、结果是否能写入审计轨迹。真实系统还要增加超时、幂等键、重试上限、速率限制和敏感参数脱敏。

[`tools.py`](./src/multitool_agent/tools.py) 的六类工具都是安全 mock。计算器只接受固定算子，不用 `eval`；文件读取查内存映射；Web 搜索查固定快照；邮件只创建草稿。

## 4. 任务和轨迹怎么构造

一条任务至少包含 `task_id`、用户指令、初始状态、目标状态和允许工具。轨迹保存每一步 action、observation、停止原因、最终回复和最终状态。

任务集应覆盖：

1. 单工具直接完成；
2. 多工具有顺序依赖；
3. 缺少必要参数，需要先追问；
4. 工具返回错误，需要换路径或停止；
5. 用户要求执行未授权或高风险动作；
6. observation 含有试图改变系统规则的文本。

训练集与测试集按任务模板、实体组合和初始状态分组。只替换姓名或日期的样本仍属于同一模板，不能随机分到两边。

## 5. GRPO 奖励

同一任务从同一初始状态复制出多个隔离环境，分别采样轨迹。奖励分成：

- `goal_state_match`：最终状态是否满足目标；
- `tool_calls_valid`：工具名、参数和调用顺序是否合法；
- `policy_compliant`：是否遵守权限和确认规则；
- `final_answer_consistent`：最终回复是否与真实执行结果一致；
- 循环、越权、无效调用和步数成本惩罚。

[`rewards.py`](./src/multitool_agent/rewards.py) 展示了轨迹级奖励和组内相对优势。所有候选的 reward 相同时，这组优势应为 0；数值稳定用的 `eps` 不能凭空制造训练信号。

`configs/grpo.yaml` 记录奖励权重和轨迹预算，它是实验设计稿。接入 VeRL 时要锁定版本，并把环境执行、终态检查和 reward 返回接到对应版本的 Agent rollout 接口。

## 6. 怎样判断任务成功

成功与否由 goal state verifier 决定。例如“创建邮件草稿但不要发送”，至少检查草稿数、收件人、主题、正文要点和发送记录。最终回复写得再像成功，只要状态没变，就记为失败。

工具选择与参数正确性可以参考函数调用评测；多轮任务还要检查顺序、依赖和最终状态。外部 benchmark 只能补充比较，项目自己的 mock 环境仍要提供确定性 verifier。

## 7. 评估与稳定性

每条任务至少运行四次，报告：

- task success rate；
- `pass^1` 与 `pass^4`，其中 `pass^k` 表示同一任务连续 k 次都成功；
- invalid tool call rate、unsafe action rate、循环率和超步数率；
- 最终回复与环境终态一致率；
- 平均调用次数、平均步数、Token、延迟和工具成本。

[`evaluation.py`](./src/multitool_agent/evaluation.py) 用 `pass_pow_k` 避免与代码生成里的 `pass@k` 混淆。测试时固定任务、初态、工具版本和采样参数，否则多次运行没有可比性。

## 9. 简历怎么写

这段可以作为简历结构参考，**其中数字不是仓库实测**。使用时换成自己的任务集、轨迹和终态结果。

**多功能任务智能体｜Qwen3、JSON Schema、Tool Calling、GRPO、VeRL**

- 设计计算器、文件只读、日历查询、邮件草稿、待办事项和 Web 搜索六类工具，统一 action/observation 协议，以 mock 状态隔离有副作用操作；
- 构造 1800 条单工具、多工具、缺参追问、失败恢复和拒绝执行任务，按模板与实体切分为 1200/300/300；
- 基于终态成功、工具合法、策略遵守和成本约束设计 GRPO 奖励，在 300 条测试任务上将成功率由 64.0%（192/300）提升到 78.0%（234/300），含无效工具调用的任务由 28 条降至 9 条，平均调用次数由 4.8 降至 4.1；
- 建立 100 条越权、提示注入和高风险动作安全集，将产生不安全 action 的任务由 14 条降至 4 条，并重复运行测试任务四次报告 `pass^4`。

## 10. 面试官可能会问

**Agent 和固定工作流有什么区别？**

回答要点：固定工作流由程序预先决定步骤；Agent 根据当前状态选择下一步。路径稳定、规则明确的流程优先写成工作流，只有分支确实依赖上下文时才交给模型。

**怎样判断任务真的完成？**

回答要点：比较 mock 数据库、文件、草稿或待办的最终状态与标注目标，同时检查最终回复是否与真实工具结果一致。模型自报成功不能作为金标。

**`pass^k` 和 `pass@k` 有什么区别？**

回答要点：这里沿用工具 Agent 可靠性评测里的 `pass^k`，要求同一任务连续 k 次都成功；代码生成常见的 `pass@k` 关注 k 个候选中至少一个通过。两个指标方向相反，不能混用。

**怎样防止无限循环？**

回答要点：最大步数、重复 action 检测、错误重试上限和无进展检测一起使用；训练中惩罚循环轨迹，评测中单独报告超步数率。

**为什么不能只奖励 JSON 格式正确？**

回答要点：格式正确只说明 action 能被解析，不代表工具选对、参数正确或任务完成。主要奖励必须来自环境终态，格式和合法性只做过程约束。

**Prompt Injection 为什么更危险？**

回答要点：网页和文件内容会作为 observation 回到模型，恶意文本可能诱导它调用高权限工具。外部内容必须按低信任数据处理，权限和确认由执行器强制，不能依赖模型自律。
